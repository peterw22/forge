# Forge authenticated push relay implementation plan

## 1. Purpose and boundaries

Forge needs reliable notifications after iOS suspends or terminates the Flutter process. The existing Android foreground service and WebSocket notification path can remain in place initially. A Cloudflare Worker will become the authorization and delivery boundary for iOS APNs and can later add FCM without changing the trust model.

The design has three independent key classes:

1. **Device identity key** — generated on each Forge installation; private key remains in the iOS Keychain/Secure Enclave or Android Keystore.
2. **Agent identity key** — generated by each `pi-go-agent` installation; private key remains on the agent host.
3. **APNs provider key** — the Apple `.p8` key stored only as a Cloudflare Worker secret.

Device and agent public keys establish who may authorize and request notifications. The APNs provider key only allows the Worker to deliver an already-authorized request to Apple.

## 2. Security goals

- The Worker never receives a device or agent identity private key.
- The agent never receives an APNs/FCM device token.
- Registering an identity grants no push permission by itself.
- Only the device can authorize or revoke an agent/device relationship.
- Every authenticated request is signed and replay protected.
- Agents submit semantic events, not arbitrary notification titles or bodies.
- Notification payloads contain IDs only, never prompts, code, tool arguments, paths, or credentials.
- A leaked device ID, agent ID, APNs token, or D1 dump is insufficient to forge a notification request.
- A compromised agent can notify only devices and event scopes that explicitly authorized that agent.

## 3. Cryptographic profile

Use one interoperable profile throughout:

- Identity algorithm: ECDSA P-256 with SHA-256.
- Public-key encoding: JWK containing `kty`, `crv`, `x`, and `y`.
- Signature encoding: IEEE P1363 raw `r || s`, exactly 64 bytes, base64url without padding.
- IDs/nonces/challenges: at least 128 random bits, base64url without padding.
- Hash encoding: SHA-256, base64url without padding.
- Clock window for authenticated requests: ±300 seconds.

### 3.1 Registration proof

A registration challenge signs exact UTF-8 bytes returned by the Worker as `signingPayload`. The payload is bound to:

- protocol version;
- principal type (`device` or `agent`);
- principal ID;
- challenge ID and random challenge;
- public-key fingerprint;
- expiration.

The Worker must not reconstruct a client-provided variation of this payload; it verifies the stored exact bytes.

### 3.2 Authenticated HTTP requests

Authenticated device and agent endpoints use these headers:

```text
X-Forge-Principal-Type: device | agent
X-Forge-Principal-ID: <stable random ID>
X-Forge-Timestamp: <Unix seconds>
X-Forge-Nonce: <random base64url value>
X-Forge-Signature: <base64url raw P-256 signature>
```

The signed bytes are:

```text
FORGE-REQUEST-V1
<METHOD>
<URL pathname>
<TIMESTAMP>
<NONCE>
<base64url SHA-256 of exact request body bytes>
```

Query parameters are not used on signed endpoints. If they are added later, the protocol must define canonical sorting before use.

## 4. End-to-end flows

### 4.1 Device first launch

1. Forge generates a random `deviceId` and P-256 identity key.
2. iOS stores the private key as non-exportable in Keychain/Secure Enclave when available, with a Keychain fallback for unsupported devices. Android uses Android Keystore.
3. Forge calls `POST /v1/registration-challenges` with its ID, platform, public JWK, and optional display name.
4. Forge signs the returned `signingPayload`.
5. Forge calls `POST /v1/registrations` with the challenge ID and signature.
6. iOS requests notification permission and registers with APNs.
7. Whenever APNs supplies or rotates a device token, Forge sends a signed `PUT /v1/devices/{deviceId}/push-endpoint` directly to the Worker.
8. The Worker encrypts the token before placing it in D1 and stores a token hash for uniqueness.

A reinstall creates a new identity unless a future migration explicitly preserves the Keychain identity. Old endpoints are disabled when APNs reports them invalid or by scheduled cleanup.

### 4.2 Agent first push setup

1. `pi-go-agent` generates a random `agentId` and P-256 identity key.
2. It stores the identity in `~/.pi-go/push/` with directory mode `0700` and private-key file mode `0600`.
3. It performs the same challenge/proof registration flow using principal type `agent`.
4. It stores only the relay URL, agent ID, private key, public fingerprint, and registration status locally.

Key loss or explicit rotation requires pairing again. Identity replacement must never silently overwrite an existing D1 principal.

### 4.3 Pairing an agent and device

1. During the Forge WebSocket handshake, Forge sends its `deviceId` and public-key fingerprint.
2. The agent sends its `agentId`, public JWK, fingerprint, and a signature over a Forge-generated connection nonce. Forge rejects an unexpected identity change for a saved endpoint.
3. The agent sends a signed `POST /v1/agents/{agentId}/pairings` specifying the target device and requested scopes.
4. The Worker creates a single-use pairing with a five-minute expiry and six-digit verification code.
5. The agent sends the pairing ID and verification code to Forge over the already-open WebSocket. Both agent UI/log and Forge display the code and fingerprints.
6. Forge fetches pairing details directly from the Worker with a signed device request.
7. The user approves scopes in Forge.
8. Forge signs the Worker's pairing `signingPayload` and submits it directly to `POST /v1/devices/{deviceId}/pairings/{pairingId}/approve`.
9. The Worker verifies both the authenticated HTTP request and the explicit pairing approval signature, then creates the authorization.
10. The agent polls its signed pairing-status endpoint and records only that pairing succeeded; D1 remains authoritative.

Initial scopes:

- `notify.approval`
- `notify.completed`

Do not implement wildcard scope matching. Every event type maps to one exact known scope.

### 4.4 Sending an event

1. The agent observes a server-side state transition:
   - approval starts waiting → `approval_required`;
   - active run becomes idle → `session_completed`.
2. It creates a stable idempotency key, for example `sessionId:approval:approvalId` or `sessionId:completed:runId`.
3. It sends a signed `POST /v1/agents/{agentId}/events` with target device, event ID, event type, and session ID.
4. The Worker verifies identity, timestamp, nonce, signature, authorization, scope, rate limit, and idempotency.
5. The Worker decrypts the device token and sends a fixed APNs template.
6. The Worker records delivery status and disables tokens rejected as unregistered/invalid.

### 4.5 Foreground and notification tap behavior

The relay always sends authorized pushes. Presence suppression stays on-device to avoid stale heartbeat state:

- iOS native code tracks the currently visible `agentId/sessionId`.
- `UNUserNotificationCenterDelegate.willPresent` suppresses a push only if it matches the visible session.
- Pushes for another connection or session show while Forge is foregrounded.
- Background or terminated apps receive normal APNs presentation.
- Once remote APNs delivery is active, iOS local notifications for the same server events must be disabled to avoid duplicates.

On notification tap, Forge reads `agentId`, `sessionId`, `event`, and `eventId`, finds the persisted endpoint, verifies the agent identity, reconnects, switches sessions, obtains a snapshot/catch-up, and shows an approval only if it remains pending.

## 5. Worker API

### Public bootstrap endpoints

- `GET /healthz`
- `POST /v1/registration-challenges`
- `POST /v1/registrations`

Bootstrap endpoints are rate-limited by Cloudflare rules and application limits. Registration cannot replace an existing ID with another key.

### Signed device endpoints

- `PUT /v1/devices/{deviceId}/push-endpoint`
- `DELETE /v1/devices/{deviceId}/push-endpoint`
- `GET /v1/devices/{deviceId}/pairings/{pairingId}`
- `POST /v1/devices/{deviceId}/pairings/{pairingId}/approve`
- `GET /v1/devices/{deviceId}/authorizations`
- `DELETE /v1/devices/{deviceId}/authorizations/{agentId}`

### Signed agent endpoints

- `POST /v1/agents/{agentId}/pairings`
- `GET /v1/agents/{agentId}/pairings/{pairingId}`
- `POST /v1/agents/{agentId}/events`

All responses include `Cache-Control: no-store`. Errors use a stable JSON shape:

```json
{"error":{"code":"invalid_signature","message":"Request signature is invalid"}}
```

## 6. D1 data model

The first migration contains:

- `devices` and `agents`: public identities, fingerprints, display metadata, revocation times.
- `registration_challenges`: short-lived proof-of-possession challenges.
- `push_endpoints`: encrypted provider token, token hash, APNs environment/topic, disable state.
- `pairing_challenges`: requester, target, requested scopes, exact signing payload, code hash, expiry and consumption state.
- `authorizations`: device-controlled agent grants and scopes.
- `request_nonces`: replay protection with expiration.
- `push_events`: idempotency and APNs delivery audit without sensitive content.
- `rate_limits`: coarse per-principal event buckets.

D1 foreign keys are enabled in migrations. Scheduled cleanup removes expired challenges, nonces, old event records, and long-disabled endpoints.

## 7. APNs delivery

Worker encrypted secrets:

- `APNS_PRIVATE_KEY_P8`
- `APNS_KEY_ID`
- `APNS_TEAM_ID`
- `PUSH_TOKEN_ENCRYPTION_KEY` — 32 random bytes, base64url encoded

Non-secret configuration:

- default topic `com.tingouw.forge`
- allowed topics and environments (`development`, later `production`)

The Worker creates an ES256 provider JWT with a lifetime below one hour and caches it in an isolate. APNs requests use:

- development: `https://api.sandbox.push.apple.com`
- production: `https://api.push.apple.com`
- `apns-topic: com.tingouw.forge`
- `apns-push-type: alert`
- `apns-priority: 10`
- `apns-collapse-id`: hash of agent/session/event class

Payload example:

```json
{
  "aps": {
    "alert": {"title": "Forge needs your feedback", "body": "Approval required"},
    "sound": "default",
    "thread-id": "<agentId>",
    "category": "FORGE_APPROVAL"
  },
  "agentId": "...",
  "sessionId": "...",
  "event": "approval_required",
  "eventId": "..."
}
```

APNs `410`, `Unregistered`, `BadDeviceToken`, or `DeviceTokenNotForTopic` disables the endpoint. Retry only transient APNs failures (`429` and `5xx`) with bounded backoff; Durable Objects or Queues should be added before high-volume use because a Worker request is not a durable job queue.

## 8. Cloudflare controls

- Put the API behind a dedicated hostname such as `push.forge.example`.
- Apply WAF/rate-limit rules to registration and pairing creation endpoints.
- Reject bodies over a small fixed limit (for example 16 KiB).
- Restrict methods and content type.
- Configure D1 backups/time-travel.
- Keep logs free of signatures, device tokens, notification payload IDs where unnecessary, and private metadata.
- Add Worker Analytics observability for status classes and APNs reason codes only.
- Optionally protect administrative inspection endpoints with Cloudflare Access; no admin API is part of the public Worker initially.

## 9. Implementation phases

### Phase A — Worker foundation (created in `worker-push/`)

- Wrangler TypeScript project and D1 binding.
- D1 migration.
- Registration proof endpoints.
- Signed-request authentication and nonce replay protection.
- Device endpoint registration with AES-GCM token encryption.
- Pairing, approval, authorization listing/revocation.
- Semantic event endpoint and direct APNs delivery.
- Unit tests for canonical signing, signature verification, scope mapping, and payload templates.

### Phase B — iOS device identity

- Native key service and method channel.
- Secure identity creation/retrieval and P-256 signing.
- APNs token callbacks forwarded to Dart.
- Worker registration client with retries and token rotation.
- Notification delegate selected-session suppression and tap routing.
- Disable duplicate local notifications after remote registration succeeds.

### Phase C — Go agent identity and protocol

- Generate/store P-256 identity with strict filesystem permissions.
- Implement canonical request signing exactly as specified.
- Add WebSocket commands/events for device identity, server identity proof, pairing request/status, and revocation state.
- Trigger relay events from authoritative runtime transitions rather than Flutter-observed events.
- Ensure one transition emits one stable event ID.

### Phase D — reliability and operations

- Cloudflare Queue between accepted events and APNs delivery.
- Retry/backoff/dead-letter handling.
- Scheduled D1 cleanup.
- Production APNs environment and TestFlight testing.
- Key rotation for APNs, device identities, and agent identities.
- Metrics and alerting.

### Phase E — optional Android FCM

- Keep the current foreground-service WebSocket initially.
- Add FCM token as another `push_endpoints.provider` value later.
- Reuse device identity, pairing, authorization, signed agent events, and idempotency.
- Select one Android notification authority at a time to avoid duplicates.

## 10. Test matrix

### Cryptography and API

- Correct registration proof succeeds; altered payload/key/signature fails.
- Existing identity cannot be replaced with another public key.
- Signed request fails for altered method/path/body/timestamp/nonce.
- Reused nonce fails even with a valid signature.
- Expired registration and pairing challenges fail.
- Agent cannot approve its own pairing.
- Device cannot approve a pairing targeting another device.
- Scope escalation and unknown event types fail.
- Duplicate event ID does not deliver twice.
- Revoked authorization immediately blocks delivery.
- Token ciphertext cannot be used without the Worker encryption secret.

### iOS integration

- Permission allowed/denied and later changed in Settings.
- APNs token registration and rotation.
- Foreground selected session suppresses; another session displays.
- Background display after Flutter suspension.
- Terminated app receives push and reconnects to the correct session on tap.
- Agent identity mismatch blocks reconnect/navigation.
- Sandbox development build and production TestFlight build.

### Failure behavior

- Worker/D1 unavailable does not break normal agent use.
- APNs timeout returns a retryable result without duplicate event creation.
- Invalid token is disabled.
- Revoked/lost device and agent keys require explicit re-pairing.
- Clock skew produces a clear error and does not weaken replay protection.

## 11. Deployment checklist

1. Create a D1 database and put its ID in `worker-push/wrangler.toml`.
2. Apply migrations locally and remotely.
3. Set the four Worker secrets.
4. Deploy to a staging hostname.
5. Run registration and pairing tests with generated non-production identities.
6. Enable Push Notifications for `com.tingouw.forge` in Apple Developer configuration.
7. Verify the provisioning profile contains the correct `aps-environment`.
8. Test sandbox APNs on a physical iPhone.
9. Add production APNs/TestFlight only after sandbox behavior and revocation are verified.
10. Add Queue-based durable delivery before exposing the service to multiple users.

## 12. Explicit non-goals for the initial Worker

- No arbitrary notification content.
- No prompt or transcript synchronization.
- No user-account system.
- No browser push.
- No administrative mutation API.
- No replacement for TLS; all communication remains HTTPS/WSS.
- No claim that local iOS notifications work after suspension—the remote APNs path is required for that case.
